# Data dictionary — synthetic mobile payment transactions

> **All data in this repository is synthetic**, generated by
> `src/generate_transactions.py` with a fixed seed. No real customers,
> devices, merchants, or payments are represented.

## Base transaction table (`data/raw/part-*.parquet`)

| column | dtype | description |
|---|---|---|
| `txn_id` | int32 | unique synthetic transaction id, 0 … 6,299,999 |
| `ts` | int32 | event time, epoch seconds (synthetic window: 2026-01-01 → 2026-03-01, 60 days) |
| `customer_id` | int32 | synthetic customer key (150,000 customers) |
| `device_id` | int32 | synthetic device key (350,000 devices) |
| `merchant_id` | int32 | synthetic merchant key (40,000 merchants) |
| `mcc` | int8 | merchant category index 0–9 (grocery … luxury travel) |
| `amount` | float32 | transaction amount, USD |
| `channel` | int8 | 0 = mobile app, 1 = web, 2 = API |
| `auth_method` | int8 | 0 = biometric, 1 = PIN, 2 = OTP, 3 = none |
| `state_id` | int8 | US state index of the transaction location |
| `lat` / `lon` | float32 | transaction coordinates (jittered around customer home / random for fraud) |
| `is_fraud` | int8 | synthetic label: 1 = fraud (exactly 8,190 rows, 0.13%), 0 = legitimate |
| `fraud_type` | int8 | diagnostic subtype label (synthetic): 0 = legitimate, 1 = obvious cash-out fraud, 2 = small probe fraud, 3 = sophisticated fraud (legitimate-looking profile, anomalous amount only) |

### Fraud injection pattern (synthetic fraudster behavior)
Three subtypes (labeled in `fraud_type` for analysis):
- **obvious cash-out** (~56%, `fraud_type=1`): large amounts (lognormal, median
  ≈ $180, capped at $8,000), 80% night-time, brand-new device (85%) or a known
  device (15%, account takeover), unfamiliar merchant, weak authentication
  (none/OTP bias), web-channel bias
- **probe** (~24%, `fraud_type=2`): tiny amounts ($1–$10) that blend in with
  legitimate traffic, otherwise the obvious-fraud profile
- **sophisticated** (20%, `fraud_type=3`): mid-size amounts (median ≈ $270,
  blending into the legitimate big-purchase tail) with a fully
  legitimate-looking profile — daytime, known device, familiar merchant,
  local geography, biometric auth. Only the amount is anomalous, so these are
  the hardest to catch and carry a meaningful share of fraud dollars.
- Realistic overlap: 20% of obvious frauds are daytime; 50% are local (not
  far-from-home); 3% of *legitimate* transactions are far-from-home travel and
  2% are on newly-upgraded devices, so no single attribute separates the classes.

## Feature table (`data/features/feat-*.parquet`) — 35 features

Rows are in ascending-`ts` order, positionally aligned with the ts-sorted raw
table. All windowed features are **trailing-only** (strictly prior
transactions; no leakage). See `sql/features.sql` for the Spark SQL port.

| # | feature | description |
|---|---|---|
| 1–2 | `dev_cnt_1h`, `dev_amt_1h` | device txn count / amount, trailing 1h |
| 3–4 | `dev_cnt_24h`, `dev_amt_24h` | device txn count / amount, trailing 24h |
| 5–6 | `dev_cnt_7d`, `dev_amt_7d` | device txn count / amount, trailing 7d |
| 7 | `dev_distinct_cust` | distinct customers ever seen on this device (sharing signal) |
| 8–9 | `cust_cnt_1h`, `cust_amt_1h` | customer txn count / amount, trailing 1h |
| 10–11 | `cust_cnt_24h`, `cust_amt_24h` | customer txn count / amount, trailing 24h |
| 12–13 | `cust_cnt_7d`, `cust_amt_7d` | customer txn count / amount, trailing 7d |
| 14 | `cust_new_device_flag` | 1 if customer never used this device before |
| 15–16 | `merch_cnt_24h`, `merch_amt_24h` | merchant txn count / amount, trailing 24h |
| 17–18 | `merch_cnt_7d`, `merch_amt_7d` | merchant txn count / amount, trailing 7d |
| 19 | `dev_hrs_since_last` | hours since previous txn on this device (720 if none) |
| 20 | `cust_hrs_since_last` | hours since customer's previous txn (720 if none) |
| 21 | `cust_amt_z` | amount z-score vs customer's expanding history |
| 22 | `dev_amt_z` | amount z-score vs device's expanding history |
| 23 | `cust_amt_ratio_mean` | amount / customer's expanding mean amount |
| 24 | `dev_amt_ratio_mean` | amount / device's expanding mean amount |
| 25 | `is_night` | 1 if local hour in 00:00–05:59 |
| 26 | `hour` | hour of day 0–23 |
| 27 | `dow` | day of week, Monday = 0 |
| 28 | `is_weekend` | 1 if Saturday/Sunday |
| 29 | `cust_geo_dist_km` | haversine distance from customer's previous txn location |
| 30 | `cust_geo_vel_kmh` | implied travel speed since previous txn (impossible-travel signal) |
| 31 | `cust_new_merchant_flag` | 1 if customer never transacted with this merchant before |
| 32 | `dev_cnt_24h_7d_ratio` | device 24h count / (7d count + 1): burst ratio |
| 33 | `amount` | raw transaction amount |
| 34 | `channel` | 0 = mobile app, 1 = web, 2 = API (LightGBM categorical) |
| 35 | `auth_method` | 0 = biometric, 1 = PIN, 2 = OTP, 3 = none (LightGBM categorical) |

## Time splits

| split | synthetic days | use |
|---|---|---|
| train | 0–40 (Jan 1 – Feb 10) | all frauds + 8.5% downsample of legitimate txns |
| validation | 41–45 | early stopping / threshold analysis |
| holdout | 46–59 (Feb 15 – Mar 1) | **full** holdout: every reported metric is measured here |
